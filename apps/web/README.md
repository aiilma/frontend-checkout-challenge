# Фронтенд `@checkout/web`

Каталог, корзина, оформление, тестовая оплата, страница заказа и список заказов поверх готового API. Состояние живёт на сервере, у фронтенда в `localStorage` только токен сессии.

## Запуск

Node.js 24, npm 11, команды из корня репозитория.

```sh
npm ci                # зависимости всего workspace
npm run dev           # API на http://localhost:4000
npm run dev:web       # фронтенд на http://localhost:5173, во втором терминале
```

```sh
npm run build:web                    # контракты и фронтенд в apps/web/dist
npm run preview -w @checkout/web     # собранный фронтенд
npm run check:web                    # lint, typecheck, тесты фронтенда
npm run check                        # плюс форматирование, бэкенд и OpenAPI
```

Адрес API в `VITE_API_URL` (`apps/web/.env.example`), по умолчанию `http://localhost:4000`. После `npm run data:reset` приложение получит 401 на старый токен и заведёт новую сессию само.

## Стек

Vite 8, React 19 с React Compiler, TypeScript strict, react-router 8, TanStack Query 5, axios, zod 4, react-hook-form, Tailwind CSS 4, примитивы shadcn на Radix, Vitest, Testing Library, msw.

## Слой API

Все запросы идут через `src/shared/api`. Дальше него `Response`, `AxiosError`, `response.ok` и `response.json()` не встречаются: хуки получают данные или `ApiError`.

| Файл                         | Что делает                                                                                                                                                                                                                      |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `client.ts`                  | Экземпляр axios: базовый адрес, таймаут, `Accept`.                                                                                                                                                                              |
| `request.ts`                 | `request<T>(endpoint)` и `requestWithMeta<T>(endpoint)` с `retryAfterMs` из `Retry-After`. Подставляет токен и `Idempotency-Key`, разбирает конверт, приводит ошибку, после `401` обновляет сессию и повторяет запрос один раз. |
| `envelope.ts`                | Разбор `{ data, meta }`; `204` даёт `undefined`, чужой формат даёт ошибку разбора.                                                                                                                                              |
| `error.ts`                   | `ApiError` с `kind` (`network`, `http`, `parse`), `code`, `status`, `message`, `fields`, `requestId`.                                                                                                                           |
| `session.ts`                 | Токен гостевой сессии, одно создание при параллельных запросах, обновление после `401`.                                                                                                                                         |
| `query-client.ts`            | `QueryClient`: повтор только сетевых ошибок, `staleTime` 60 с, ошибка хуков типизирована как `ApiError`.                                                                                                                        |
| `use-idempotent-mutation.ts` | Ключ идемпотентности для заказа и попытки оплаты.                                                                                                                                                                               |
| `polling.ts`                 | Опции опроса для `useQuery`: пока данные в обработке, до результата или неповторяемой ошибки.                                                                                                                                   |

`Endpoint` различает методы: `GET` и `DELETE` без тела, `POST` и `PUT` с телом и ключом идемпотентности. Флаг `public` убирает токен у `/api/products`, `/api/sandbox` и `/api/sessions`.

Новый запрос это одна функция рядом с сущностью, например в `entities/cart/api/cart.api.ts`:

```ts
export const setCartItem = ({ productId, quantity }: CartItemInput) =>
  request<CartItem>({ method: 'PUT', path: `/api/cart/items/${productId}`, body: { quantity } });
```

Ключ идемпотентности живёт в `useIdempotentMutation`. Пока предыдущая попытка не получила ответа сервера и тело совпадает, ключ тот же; любой ответ сервера закрывает попытку, следующий вызов получает новый UUID. Двойное нажатие и повтор после обрыва сети создают один заказ, новая попытка оплаты после отказа уходит с новым ключом.

`failed` и `cancelled` приходят в успешном ответе о попытке оплаты, их разбирает страница оплаты. На `409 QUOTE_EXPIRED` и `409 CART_VERSION_CONFLICT` при расчёте или создании заказа фронтенд перечитывает корзину и расчёт, введённая форма остаётся. Прочие ошибки расчёта показываются в итоге с кнопкой «Повторить».

## Обработка данных

Самый частый участок: индекс позиций корзины по `productId` в `entities/cart/api/use-cart.ts` через `shared/lib/index-by.ts`.

```ts
export const indexBy = <T, K>(items: readonly T[], keyOf: (item: T) => K) => {
  const index = new Map<K, T>();
  for (const item of items) index.set(keyOf(item), item);
  return index;
};
```

Индекс строится заново только при новой ссылке на `items`: React Compiler мемоизирует вызов, TanStack Query сохраняет ссылки на неизменившиеся части ответа. После смены количества одной позиции остальные позиции приходят с прежними ссылками, и их карточки и строки не пересчитывают разметку.

Один проход по позициям, одна вставка в `Map` на позицию, без промежуточных массивов; карточка каталога берёт свою позицию через `itemsById.get` за константное время. С `items.find` внутри карточки поиск был бы линейным на каждую карточку при каждой перерисовке.

В памяти одна `Map` с записью на позицию и ссылки на объекты из ответа, без копий. `quantity` и `subtotal` приходят с сервера и показываются как есть.

Так же устроены `productsById` на странице корзины и пустые массивы-константы вместо `?? []`, чтобы не создавать новую ссылку на каждый рендер.

## Проверено

65 тестов в `npm run check:web`, HTTP мокируется через msw.

- Слой API: конверт и `204`, три вида ошибок, создание сессии и одна сессия при параллельных запросах, повтор после `401`, `Idempotency-Key`, `Retry-After`, правило ключа, опрос до результата и его остановка при размонтировании и ошибке.
- Каталог и корзина: данные из API, остаток блокирует добавление, изменение количества и удаление, ошибки загрузки и строки с повтором.
- Оформление: расчёт при выборе пункта выдачи и курьера, конфликт версии корзины и сбой расчёта, ошибки полей на blur и от сервера с тем же текстом, что у схемы, заказ картой с ключом, наличные без онлайн-оплаты, устаревший расчёт при создании заказа, пустая корзина.
- Оплата: карты из sandbox, попытка с ключом, успех с опросом, отказ и новая попытка с новым ключом, отмена, отмена при уходе со страницы, продолжение после перезагрузки.
- Заказ и заказы: три исхода заказа, скелет до ответа сервера вместо кэша, список заказов сессии.

Руками в Chrome на 1280 и 390 px: оплата картой с отказом, новой попыткой и перезагрузкой во время обработки, наличные, отмена оплаты, форма с клавиатуры, без горизонтальной прокрутки на 320 px. `npm run smoke` проходит.

## Решения

- Vite, а не Next.js: приложение клиентское, сессия и заказ восстанавливаются из `localStorage` и адреса страницы.
- Кэш, дедупликация, отмена и опрос на TanStack Query, свой слой поверх задаёт транспорт, конверт, ошибку и ключ.
- Ключ расчёта доставки включает версию корзины и параметры доставки, адрес собирается с задержкой 400 мс.
- Попытка оплаты создаётся при открытии формы, поэтому «Отменить оплату» отправляет сценарий `cancel`; уход со страницы навигацией браузера отменяет нетронутую попытку так же; после перезагрузки берётся активная попытка из списка заказа.
- Серверные ошибки полей показываются текстом схемы этого поля по пути из `fields[].path`, тексты ajv не разбираются.
- Серверные `links` не читаются, «можно ли оплатить» выводится из полей заказа в `orderOutcome`.
- Интервал опроса из `Retry-After`, по умолчанию секунда; опрос только в `processing`, `staleTime` запроса равен интервалу.

## Не сделано

- Оптимистичных обновлений корзины нет, после изменения количества корзина перечитывается.
- Расчёт для курьера идёт только после валидного адреса.
- Закрытие вкладки во время оплаты не отменяет попытку: она остаётся `pending` и переиспользуется при возврате.
- End-to-end тестов в браузере нет.
